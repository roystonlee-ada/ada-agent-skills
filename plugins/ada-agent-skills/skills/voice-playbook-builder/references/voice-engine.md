# The voice engine — what it does to your playbook

Chat probes pass and the call still goes wrong. These are the behaviours you cannot see in JSON. Read this when a
call surprises you or you need the reason behind a checklist row; the fixes themselves are in the checklist and `patterns.md`.

## Behaviours and the design that survives them

| Engine behaviour | What you see on a call | Design that survives it |
|---|---|---|
| **Loops don't repeat the way you expect** — exact sends DO replay each pass, but a contextual ask re-entered by `go_to` with the default `only_when_needed` re-extracts the previous item's answer and skips the question; a generative set re-reads the whole transcript; an exact set that concatenates strings fails to parse and the write is lost (this is how the engine's re-ask loop works) | Names accumulate wrong, second membership's confirm never spoken, "cancelled both" when one ran | Decide everything once before the loop (EvalJS categorizer). Loop body = RUN + IF + SET index + GOTO, nothing spoken. Accumulate results inside the picker action, not in SET steps. One summary after. |
| **Backtrack detector** (always on; mechanics and design rules in `voice-engine-internals.md`) — on every reply to an `ask`, a parallel LLM call decides whether the caller is correcting an EARLIER answer; if so it jumps back to that step and clears everything collected after it | "I'd rather pause" at the discount ask restarts selection; a variable resets and an earlier question is asked again; downstream answers vanish. We first logged this as "engine rewind" | Fix ladder, cheapest first: (1) tell each ask what to do with replies aimed at an earlier step ("rather pause" here = capture `no`); (2) reword the colliding option so it stops mirroring the earlier step; (3) the real fix: no two asks own the same answer. Confirms phrase an explicit question ("Shall I go ahead?"). Store silent-SET values as tokens a caller won't say. |
| **Latency filler** — when the first turn's actions take >2 s the engine speaks a generated line (`is_acknowledgement:false`, "I'm still processing…") | Filler that claims progress before anything ran | Not playbook-controllable. Constrain the playbook-level `acknowledgment_instruction` to one sentence and forbid "processing/checking/looking up". Interstitial audio is a channel setting. |
| **Acknowledgment paraphrase** — the playbook-level `acknowledgment_instruction` is paraphrased with the caller's words | "I'm still processing your cancellation request and checking options" | Either constrain to one warm sentence, or `say exactly "<text>"` for fixed wording. Set expectations here: "I can cancel that for you on this call. First I'll verify your identity." |
| **Generative drift** — instructions asked to acknowledge or fill time invent completion | "Your memberships have been cancelled successfully" before the loop | Fillers and acknowledgments are exact `send` messages. |
| **Dead air** — silent SET/RUN chains | Caller thinks the line dropped | One exact filler before a slow action block; never one per action. |
| **`send` does not wait** — it emits and the engine advances at once; on voice the next step runs while TTS is still playing | "Asked me twice", "didn't wait for my answer" (the most common voice sim failure); a `send` before an action or handoff gets truncated or collides | Every question is an `ask` (it blocks until the caller answers). `send` only for statements nothing depends on: fillers before silent work, terminal answers, the closing line. A "let me check" `send` directly before a slow action is acceptable and recommended by the improvement guide, but keep it one short utterance. |
| **`go_to` hard cap: 5 visits per target step per turn** — a 6th visit in one turn raises `infinite_loop` and halts the turn | A silent loop over 6+ items dies mid-way | A same-turn loop (no `ask` inside) processes at most 5 items. Budget retries per turn, not per conversation. For more items, process them inside an action or split across turns. |
| **Generative SETs each make an LLM call that can speak an acknowledgment** | 13 instruction-driven resets at entry → 13 back-to-back "Let me check…" and dead air | Exact `value` SETs for constants, resets and counters; generative SETs only to read the customer, always with `accepted_values` and a `fallback_value`. |
| **`null is not "X"` is false** | Unset variables sail through "is not" gates | Pair with `is null OR is not "X"`. Initialise variables you branch on. `is null` ≠ `""` ≠ `"NONE"`: the gate must check the exact sentinel the writer sets. |
| **One `send` = one TTS utterance; punctuation is the only pacing you control** — "deliver beat by beat" inside a send instruction is ignored | A list of memberships read in one breath; callers can't follow or refer back | Compose the sentence in the deterministic action and speak it with an exact `send`: count in words, one ordinal beat per item, a `"..."` between items (Ada's own CI appends `...` to acknowledgments for prosody). "I see three memberships… First, your Premium Membership... Second, your U.S. Regional Membership... And third, your Global Membership." Ordinals also make "the first one" unambiguous for the ask that follows. Build the `...` at runtime in EvalJS (`"." + "." + "."`) — see actions-and-evaljs.md. |
| **TTS normalisation is not yours to control** — "U.S." was read "U, dot, S, dot" once; "U S Regional 6 Months" became a comma-separated spelled list; dates written 2027-03-15 were read fine | Product names sound wrong | Speech-normalise names in the deterministic action before the exact send: "U.S." → "U S", "(Gift)" → "gift", digits inside names → words ("six months"). Verify every product name in a real voice sim, not by reading the text. |
| **DTMF arrives as text** — keypad digits reach the transcript as `dtmf:5550123` | Phone numbers, codes and dates typed on the keypad don't match spoken formats | Any instruction that reads digits or dates lists all three forms: spoken words, numerals, and the `dtmf:` prefix. |
| **Two exact `send`s back to back can clip** — the second utterance (or a caller barge-in) cut the first short in some sim calls | The intent ack is lost when nothing blocks between it and the next send | Put an `ask` (or a slow `run`) between consecutive sends, or merge them into one sentence. Never rely on two adjacent sends both being heard. |
| **Off-topic reply (`intent_change` / `topic_change`)** — the extractor decides the reply is about something else (a reply before the question was ever asked just gets the question). The ask's `on_off_topic` decides: `exit_playbook` (default) suspends the playbook and the general agent takes the turn; `stay_in_playbook` notes the side question and keeps the caller in the flow | Two faces. Wanted: "I'd rather cancel" at a pause ask hands straight to the cancel playbook. Unwanted: "why did you charge me?" at the auth ZIP ask dropped the caller to the fallback (seen on a reference build). The extractor also mislabels on-topic replies ("the one you just said") | **Decide per ask.** `exit_playbook` where a competing flow should take over (offers, selections that another playbook owns). `stay_in_playbook` where a side question should be answered and the task resumed (auth, data capture). `stay_in_playbook` is not yet proven live as the fix — test it in sandbox first. With the client's combined flow controls on, a question Knowledge can answer is split out as `search_question` and follows `on_off_script` instead: `search_knowledge` answers and resumes at the same question; `skip_knowledge` moves on with the fallback value. |
| **"I don't have it" (`unable_to_provide`)** — writes `fallback_value` at once and advances, skipping every re-ask; an extractor failure also returns it | "I don't know" to the card digits → value empty → the verify action ran anyway → 400 (reference auth child). A partial answer (spelling an email across turns) can be misread this way | Branch on the fallback/empty value before any action that uses it. In the instruction, say a reply that adds more of the answer is still answering; a value is unavailable only when the caller clearly says so. |
| **Exact-match replies skip the extractor** — a reply that exactly matches an accepted value or quick-reply label (case and spacing ignored) is saved directly; the instruction is never read | An instruction rule about "yes" (polarity, context) never fires when the caller says just "yes" | Don't put meaning-changing rules in the instruction for values that can be said exactly. Make the accepted value itself unambiguous. |
| **Non-2xx action status = forced handoff, unless the client has status-code output on AND a later IF reads the action's mapped status variable** | Failure branch never runs; the call transfers. Sims skip the forced handoff, so sims pass while live calls transfer | Run the setup check: it reads real transcripts for the effect. On the reference build it was on (a 400 kept the playbook stepping). Where it's off, have the API return 200 with an error field and branch on that. |
| **Decline intercepted above the steps** — "actually, never mind" mid-flow can be handled by the reasoner before any compiled step runs | No `variable_set` for the field being asked; the flow just leaves ("never mind, leave them all" → engine said "I'll leave all memberships unchanged", then the bot-level CSAT offer; our exact leave-as-is line never ran) | No step-level guard can catch it; design the re-entry (checkpoint) and the description's exclusions instead. |
| **Deviation exits** — `on_human_request: exit_playbook` hands the turn to the bot's routing | Bot-level routing playbook transfers the caller to a real queue | Fine, but know it fires during your asks. Set the checkpoint before it can. Capture `HANDOFF_REQUESTED` in your asks so you control the message. |
| **Re-entry** — after a knowledge answer or a failed transfer the playbook re-triggers from step 1 | Greeting and auth repeat | Checkpoint variable set before each question; a dispatcher after the token step jumps to it; "picking up where we left off" as the only re-entry line. |
| **Fallback re-trigger** — after a self-serve fallback the caller says "I can't get online" and the playbook fires again | The same five-step script again and again in one call | After the fallback, offer a choice (text the link / connect to an agent) and act on it; do not let the description re-trigger on the same complaint. |

The mechanics behind these rows (how backtracks are scored, leaving and re-entering, which exact SET values write,
text-to-speech rules, what the bot sets before your playbook runs, multilingual knowledge search, dashboard step numbering)
are in `voice-engine-internals.md`. Open it when you're debugging a call and the table above doesn't explain it.
